# Original offer admission before the recovery preparation claim

The fixed native product keeps its existing purchased-grant recovery owner,
recorded-result owner, spending file, wallet, wire guard and close chain. The
same stateless fixed-product binding also wraps their outer application facade.
The inner binding remains in place; no stateful owner is moved or replaced.
Both explicitly selected DP and non-DP products use this outer boundary. The
generic non-product entry remains unchanged.

Previously, the native source placed its fixed-product gate inside purchased
recovery. A coherent different offer could pass the generic preparation codec,
consume the outer recovery preparation claim and then be refused by the inner
fixed-offer gate. No spending or wire call was required for that known refusal,
yet the recovery owner retained its existing downstream-failure HELD outcome.

The outer binding first captures the complete preparation and requires both
the exact originally selected payment-required header and the same challenge
semantics. A cheaper or higher price, changed product metadata or equivalent
header reencoding cannot enter the recovery owner, its child, spending or query
custody. Accessors and proxies are rejected without invoking caller code.
A corrected original can still use its first preparation attempt. Refusing a
foreign offer after a valid preparation also leaves that existing original
available for its original commit; it does not create another preparation.
This is application-facade admission. The existing command host may terminate
on a command error; no automatic input correction, retry or reopening is added.

For an admitted original, the existing generic capture retains the same JSON
and digest. The outer binding returns the original operation and close promises
and delegates inspection to the same child. It owns no journal, key, reservation,
retry state, clock or release budget. The non-DP policy still passes its existing
separate preclaim gate. Once a child operation has been admitted, a lost or
rejected callback remains HELD and cannot authorize replacement, re-signing,
funding resend, a second query or another close attempt.

The local controls use actual pure offer, recovery, result and query components
with declared memory children, custody and transport callbacks. An explicit
legacy-order counterexample distinguishes the ordering defect from the fixed
boundary. The reference model checks one declared funding/query/grant, 100
distinct results and exact replay after a preclaim refusal. Its trusted MOCK
activation and invalid signature-shaped fixture bytes are not authenticated
funding, cryptographic proof or native execution.

Native application source receives parser checks only. Installed SDK/core,
SQLite, HTTPS, actual keys/signatures, nonce search, PREPARE, fresh-process
reopen, physical release, Linux and G0-G5 acceptance remain unestablished.
