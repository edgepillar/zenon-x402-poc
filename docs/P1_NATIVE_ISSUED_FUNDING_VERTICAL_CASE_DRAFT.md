# Actual issued funding native vertical case: source-only draft

The new case driver hardwires the actual issued-funding application, RPC-only
peer, DP funding/service client, V6 store, grant operator and bounded native
HTTPS factory. It does not replace these owners with event facades, canned
funding responses, module aliases, source transforms or injected transports.

**Status: authored source and syntax checks only. The new graph has not been
imported or executed.** The case is not eligible for main or production based
on these checks. Its pending complete runtime/package admission must include
the actual official x402 core, SDK/Noble, SQL, signer and native dependencies;
the version labels and entry guards do not establish package qualification.

## Concrete integration

The driver is `qualification/issued-funding-post-native-vertical.case.draft.mjs`.
It selects exactly one `clean` or `lost-ack` case per separately admitted Node
process. It consumes no previous one-shot allowance and resets no actual
application/module slot. The older three-case DP selection is unchanged.

The authored flow is:

1. Read new private test TLS inputs and obtain one unprivileged IPv4 port,
   observing its real close before the actual application binds that port.
   A bind race refuses; no alternate-port retry or production fallback exists.
2. Construct the actual service/intake stores, issued application and RPC-only
   TLS peer. Obtain the actual original unpaid 402 frame over native HTTPS;
   bind its original url/tags challenge into the actual DP read plan.
3. Perform bounded independent reference work and actual DP preparation with
   one synthetic transaction signer. Retain the original hash, header,
   checkpoint and binding/digest pins in an independent new file before V6
   custody. Commit the same original, then send exactly one native funding POST.
4. Require the actual application to retain BOUND separately from settlement.
   Observe the same pending continuation explicitly: pending, then success.
   The local facilitator/observer outcomes remain declared synthetic results,
   not chain publication, inclusion, finality or a real provider observation.
5. Activate the actual primary and separate foreign grants through the real
   funding composition and synthetic signed provider envelopes. Initialize
   durable execution and locally admit only the committed primary grant.
6. Close funding through its actual owner, reopen the same V6 file through the
   actual guarded handoff, restore only the retained original header and send
   the first explicit service request. Never resend the funding payment.
7. Require identical client submission to refuse without another dispatch.
   Separately send the retained exact proof/body to the actual backend and
   require cached success with no double execution/debit. A valid proof for
   the foreign grant must receive 401 from the scoped server, with no request
   reservation or debit. No new proof is generated for either replay.
8. Send a second original service request. `clean` requires actual clean
   client close. `lost-ack` initiates the real public client close from the
   second server execution callback, then requires durable server SUCCEEDED
   and exactly four consumed units while the client close stays UNKNOWN.
   **That fault's effectiveness is an unexecuted assertion, not a result.**

The driver checks original signed block/packet bytes, original hash, same-file
identity, real request counts, actual grant/request rows and credit totals.
These observations do not make a filesystem lease or authenticated chain.

## Fixed application contract

The actual application's durable service runtime now preserves
`monotonicNowNs`, `schedule` and `cancel`. Previously this composition seam
copied only the latter two, while the actual durable execution owner requires
all three. That mismatch would refuse real service admission. The ingress
runtime remains its distinct two-field contract. The driver uses real timers
and a monotonic clock, not a synthetic clock or an adapted fake session.

The two cancellation contracts also remain distinct: actual ingress
`cancel()` returns `true`; durable-service `cancel()` returns `undefined`.
This is a source-bound fix with syntax evidence, not native execution proof.

## Future per-case resource scope, not execution permission

Each case needs a separate reviewed allowance and a fresh managed task:

- Five new SQLite paths: service, intake, two observer files and one V6 payer
  file. The V6 and intake-created observer are reopened only through their
  actual intended APIs; no historical file or missing-file fallback is used.
- Two independent new pin/original files; journals, TLS inputs and bounded
  receipts are additional quota-accounted data, not disposable by default.
- Four ephemeral synthetic Ed25519 keys: one wallet, two capabilities and
  one provider. At most six signatures: one transaction, three capabilities
  and two provider envelopes. Test TLS material is separate.
- One bounded producer search of at most 4096 candidates, reference windows
  of 4096 with at most 32768 total candidates, plus a 16384 verification
  reservation. Aggregate reservation stays at most 65536; no rekey/new range
  or retry follows exhaustion. Actual producer iterations are not measured.
- Actual loopback only: RPC cap 174 connections and application cap eight,
  at most 182 total. The expected complete transcript is 90 RPC plus six
  application connections (96), not a measured result. The temporary native
  port reservation accepts no intended connection. No Node child process.
- No install, external endpoint, real wallet/payment, SDK PREPARE, live pilot,
  provider deployment, default-buyer change or production authority.

One process cannot run both modes by replacing module slots or cloning source.
The driver guards are cooperative, not an OS/filesystem/network sandbox.

## Ownership and uncertainty

Raw control requests require authenticated TLS and actual response-end,
response-complete, response-close, request-close and socket-close observations.
The actual one-second drain observer's API bound is respected; a timeout is
not rewritten as success. Failure-only native stop never qualifies release.

Normal teardown waits for actual app/RPC/observer close results and zero owned
timer/control sets before closing the handed-off idle service/intake stores.
The expected HELD V6 client is never directly closed, reopened, replayed or
deleted. Failure teardown requests independent actual native stops without
short-circuiting on one rejection, retaining unknown handles and files. No
historical root is adopted and no owner/lease record is rewritten.
