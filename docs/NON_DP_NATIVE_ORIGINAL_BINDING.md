# Non-DP native original binding: source candidate

This draft connects the fixed operator product entry to the explicitly named
non-DP application, native client, original submission and preparation owner.
Native application execution is **NOT_EXECUTED**. The V77 source profile repins the buyer catalog to this changed graph.
Catalog equality is source evidence; real runtime qualification remains required.
G0-G5 remain open.

The operator selects `openSdk105NativeNonDpApiCreditProductSelectionCommandSession`.
That fixed source path selects `openSdk105NativeNonDpApiCreditProductApplication`
and `openZenonNonDpNativeFundingServiceClientWithApiCreditWireOwner`. JSON,
module names, a zero-difficulty response or a failed DP attempt do not choose
this lane. Existing explicitly named DP entry functions retain their selection.
The original funding input must carry the explicit three-field non-DP policy.

The native client uses its SAME wire/store owner, retained read session and
age-bound context-custodied wallet. It reads the expected public key/address
from that original owner's immutable inspection and compares the public key
to the already captured configuration. Current-owner checks bracket capture
and every borrowed read. No nonce-material producer is constructed. The
legacy operational profile still captures material limits for compatibility;
those limits do not construct work or select fallback in this explicit lane.

The parent session's two-field `readOptions` object retains its exact identity
at the original-submission boundary. The explicit retained-reader candidate
entry adds the void current-owner guard only to a private borrower view; all
transport/account function identities and physical budgets remain the same.
It creates no alternate stop/close owner. Preparation-context binding happens
once inside the non-DP candidate, so the native client's older DP binder is
skipped for this lane.

`createZenonNonDpOriginalFundingPreparation` retains the genuine V6 prototype
checks and original store claim. It obtains the actual source candidate's
already encoded packet, then invokes the SAME real cryptographic payment
preflight. A successful preflight must match hash, intent and the exact signed
transaction. This is source wiring, not an observed native success.

Commit still requires independently supplied pins. Immediately before the
existing captured atomic V6 method, it calls the actual candidate's one-shot
`revalidateSignedOriginal`. The returned candidate and packet must be the
identical objects, with the same unsigned projection, signed fields and
pre-sign checkpoint text. It does not re-encode the non-DP packet. The existing
store status/revision/header/checkpoint readback checks and UNKNOWN/HELD
outcomes remain. No retry, replacement, re-signing, automatic submit or grant
authority is added.

`createZenonNonDpOriginalFundingSubmission` uses the existing guarded V4 payer
and bounded read/store close join. The application retains its original key
lease, opening custody, spending file, store/wire epoch and close paths. Real
SDK/signature/SQL/HTTPS behavior, interruption/reopen, physical release, Linux,
live chain trust and economic/product acceptance remain unestablished.

DATA controls evaluate only the pure retained-reader ABI and existing source
owner/codecs over declared memory ports with deliberately invalid
signature-shaped fixtures. Native files may receive parser-only checks;
they are never imported by these DATA tests. Passing DATA or parsing cannot
qualify native execution, installed package admission or the full product.
