# Zenon-funded x402 application roadmap

Updated 28 October 2026. The product goal is a Zenon-funded x402 application
that safely recovers the same payment and original request and supports many
metered API calls. Small order, delivery and compensation contracts belong in
this core. BTC checkout is a separate, demand-gated workstream; it does not
block the Zenon application.

Baseline: [e1d37f58](https://github.com/edgepillar/zenon-x402-poc/commit/e1d37f588b8c25087eb17cc54f5cdc7ea7e19773).
Implemented source, DATA/component results, source-bound native results, hosted
CI, authenticated economic acceptance and production readiness remain separate.
Core integration is GO. Economic pilot and production acceptance remain open.

## First package: response loss

| Acceptance ID | Required observation | Current gap |
| --- | --- | --- |
| RL-FUNDING-ACK | Funding is bound but its client reply is lost; the original signed bytes/hash and liability remain recoverable. | Native funding-reply-loss composition is open. |
| RL-SERVICE-COMMIT | Service commits before its reply is lost; one original execution/debit remains recorded. | [V5 selected case passed](P1_V5_SERVICE_RESPONSE_LOSS_QUALIFICATION.md): matching commit, one socket stop, rejected client command, one execution/two consumed units. Full delivery-loss acceptance remains open. |
| RL-EXACT-REPLAY | The exact retained request recurs without another economic operation. Similar amounts, balances or approximate history cannot substitute. | Backend native replay passed with unchanged debit/execution and foreign-grant refusal. Reopened original-client acceptance remains open. |
| RL-REOPEN | A reopened client reads the original backend outcome from the same records, without gaining current dispatch authority. | Current no-dispatch recovery source is prepared; native reopen remains open. |
| RL-LATE-CLOSE | Late success/error during close cannot repair an UNKNOWN result or bypass held ownership. | Selected loss case preserved HELD/UNKNOWN; the late success/error matrix remains open. |

Success is not merely an eventual HTTP 200. It requires unchanged original
identities, no second economic operation and no incorrectly cleared uncertainty.
The service-loss selection used its own finite native scope and its one trial
is consumed. Its result is partial response-loss acceptance; the pending case
was not rerun. Keep the remaining loss/reopen/late-close gaps open.

The next package then covers same-record interruption/recovery and native
resource lifecycle, followed by the small common contract vectors below.
Preparation-time optimization is supporting work, not a gate that stalls P1.
The new private byte-cache draft is unqualified and is not selected by native
launchers.

## Common contract: small additions to existing flows

| Vector family | Invariant |
| --- | --- |
| ORDER-IMMUTABLE | Product, beneficiary/holder, price, quantity, network and conditions cannot change after payment. |
| ORDER-DELIVERY | Funding verification does not prove service delivery; retain a separate delivery record. |
| ORDER-LATE-LIABILITY | Offer/reservation expiry does not erase verified payment; delivery or defined compensation remains owed. |
| ORDER-EXACT-PAYMENT | Match the exact original payment identity, not a similar amount or an account balance. |
| COMP-EXACT-ORIGINAL | A lost compensation reply does not authorize a second payout; preserve its separate original identity. |
| PROOF-TAGGED | Zenon signed checkpoints and Lightning proofs retain different validation/authority meanings. |

These application contracts adapt the
[pinned order/delivery research](https://github.com/edgepillar/bitcoin-payments-zenon/blob/d57acfd2aef6645299cefff49bdf42bd1c103a86/studies/resource-checkout/docs/architecture.md).
They do not require a broad multi-payment-platform refactor. Existing exact
custody and ledger components should be reused.

The first small addition is the [purchased-terms contract](../src/service-purchase-terms.js)
and its [acceptance vectors](../qualification/service-purchase-terms.behavior.mjs).
[All 18 local DATA/component cases passed](../qualification/service-purchase-terms.actual-local-result.json);
this is separate from native application and hosted CI evidence.
It captures bounded canonical terms with explicit integer price units and
compares them with the retained original; changed product, beneficiary, holder,
price, quantity, network or conditions are rejected. Its frozen snapshot is an
in-memory contract. Durable custody and payment/delivery/compensation integration
remain open; this helper does not authorize any economic action.

## P2 and Dynamic Plasma boundaries

Persisting intent before signing is insufficient by itself. If a signer
produces bytes but its reply is lost, recovery must obtain those same durable
signed bytes/hash. Otherwise keep the account uncertain and prohibit new
preparation or signing. Distinguish normal close from forced interruption,
logical CLOSED from actual release, a retired worker from one still running,
durable intent from durable signed payload, and cached backend success from
current client authority. Controlled HELD plus denied new ownership is valid
when a resource cannot be shown released.

Maintain two explicit network-rule profiles: currently verified rules and
Dynamic Plasma rules. DP work need not wait for mainnet activation. Revalidate
bounds immediately before signing; after signing, reconcile only the original.
Pilot admission independently pins the running binary, genesis, active rules
and RPC contract. A first pilot using current rules must not depend on a future
DP activation.

## Conditional BTC checkout stream

| Stage | Gate |
| --- | --- |
| B0 | Parallel demand research, proposed cap two weeks/three person-days; record a concrete price, real need, free alternatives and provider willingness. No commercial validation is claimed. |
| B1 | Only if demand persists, choose one operator and one protocol: L402 or a separately accepted exact/lnbtc adapter. |
| B2 | Local claim-reply loss, late payment, unpaid-reservation pressure, exact Fuse delivery, worker conflict and uncertain compensation acceptance. |
| B3 | Operator accepts inventory, open-order and compensation limits before a bounded pilot. |

Use the [pinned experiment plan](https://github.com/edgepillar/bitcoin-payments-zenon/blob/d57acfd2aef6645299cefff49bdf42bd1c103a86/studies/resource-checkout/docs/experiment-plan.md)
as an investment filter, not a statistical success threshold. This roadmap does
not authorize interviews/messages, provider setup, real payments or a pilot.

The critical BTC case is a consumed facilitator claim followed by a missing
application/job response. Resolve the same order without a new invoice, payment
or Fuse. Under the
[pinned Lightning scheme](https://github.com/x402-foundation/x402/blob/5847ee5a368130df48bd6ff958e1519de4c41163/specs/schemes/exact/scheme_exact_lnbtc.md),
`duplicate_settlement` is not delivery evidence. Keep explicit amount units,
the absence of a stable Lightning payer identity and the separate compensation
agreement; do not invent a generic refund or proof-conversion authority.

## Measurements and exclusions

Measure funding-to-usable-grant latency, funded API reservation/execution/result
latency, and native service delivery latency separately. Test correctness at the
bounded pilot load before sustained capacity. Then report p50/p95/p99,
uncertainty age, support burden and unit cost. Momentum cadence and DATA controls
are not TPS evidence.

PTLC, ZVM, StateRoot and a BTC bridge are not prerequisites of the first product.
Issue #173 stays outside this roadmap. Existing payment, signer, test,
publication and cleanup limits are unchanged by this document.
