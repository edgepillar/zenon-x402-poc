## Six prepared scenarios

1. Actual prepare, independent pin retention, current-read commit, exact V6
   custody, one declared BOUND response, then joined read/store close.
2. Reentrant close inside actual native recovery blocks funding POST entry
   while retaining the exact original PREPARED packet.
3. Uncertain read close permanently holds the same idle V6 store; a late
   settlement cannot promote it. No force-close, reopen or replay is selected.
4. Closing the first pending account read aborts before material or signing.
5. Closing the sixth pending account read after signing refuses custody
   without reassembly, replacement, another material request or signature.
6. A different readOptions object refuses construction before wallet/read
   entry and leaves construction-failure store ownership with the caller.

Read/close and fetch callbacks are declared synthetic capabilities, not actual
HTTPS owners. Material is fixed at declared zero difficulty; the full bounded
HTTPS/nonce-producing factory is deliberately outside this fixture. This is new
V3 close coverage, not a smaller passing replacement for V2's twelve cases.

## Prepared execution boundary

Matching direct native scope is separate from source publication. The old V2
three-run approval was exhausted: its last result remains eleven pass / one
fail. Its old profiles, failed runs and corrected unexecuted body are preserved,
not rebound to this changed V3 graph.

If the separately requested V3 scope is approved, each fresh managed task is
limited to six new V6 files, four independent pin files, one ephemeral synthetic
key, at most four transaction signatures and one in-process fetch callback.
The new root would allow at most three reviewed attempts, one Node command per
task, a 4 MiB task quota and 64 KiB caps for each output stream. The 10 GiB free-
space floor plus allocations/reservations remains mandatory; old roots and
held fixtures are not cleaned or adopted.

The launcher checks current sources/packages, runtime/manager identity, volume,
capacity and ownership before task admission and again before native entry.
It also rechecks the complete profile after exit and requires six completed
cases and exact counters before accepting an exit-zero result. Source review
already caught and corrected --import= flag handling and the manager's absence
of a stderr_limit keyword; the immutable root output policy supplies that cap.

Native-fchmod mode has no Node Permission Model or OS/network sandbox. These
source/identity/resolver checks are cooperative guards, not authentication,
authority, hard quotas, deadlines, resource-drain or crash-cleanup proof.

Installation, socket/external network, real wallet/payment/provider signing,
nonce search, SDK prepareBlock, real PREPARE and live/economic pilot are excluded.
P0-P4 runtime, native HTTPS, positive-work, crash/recovery, current-main CI and
owner/provider activation gates remain incomplete. No active buyer/default,
live signing, grant or service-delivery behavior is enabled by this draft.
